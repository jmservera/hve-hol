Exercise 6 · Open lab 3 · Parallel task · After the first RPI run

Reuse what the first RPI run taught you

Parallel taskOpen lab 3

On this pageBriefHow to startHand-in and toolkitTips
Objective

Capture one lesson from Exercise 5 as an instruction, skill or control the next run picks up.

Input
Corrections and review findings from Exercise 5, plus the auditor’s log
Best use
Parallel task, once Exercise 5 has a review
Roles (suggested)
Architect and one volunteer

Steps

  1. Find one thing you had to correct, repeat or explain to the agent in Exercise 5.

  2. Pick the smallest block: instructions file, scoped instruction, prompt, skill, hook or connector.

  3. Define when it runs, its inputs, outputs, permissions and failure behaviour.

  4. Build it with hve-builder, then re-run one RPI step to check the correction is no longer needed.

  5. Explain where it plugs into HVE-Squad and where it should stay independent.

Hand in

Tick items as your team hands them in.

Exercise 6 · How to start

Make the next run need fewer corrections

Start here

  1. 1

    Read the auditor’s log and the Exercise 5 review: what did you correct, repeat or explain to the agent?

  2. 2

    Pick one lesson that will come back: a convention, how to run your tests, a template, a triage checklist.

  3. 3

    Choose the smallest block: a line in .github/copilot-instructions.md, a scoped instruction or a skill.

  4. 4

    Create and validate it with hve-builder, then re-run one step, such as /rpi-plan, and check the fix holds.

Tips and tricks

  • A rule for the whole repo? copilot-instructions.md. A rule for some files? An instruction with a narrow applyTo.
  • Know-how, checklists or templates? A skill: a short SKILL.md with the detail in reference files.
  • A rule that must always hold? A hook or CI check (Exercise 7), not more instructions.
  • Name an owner and a version so another team can install it.

Watch out

  • Generic advice such as “write clean code”
  • A big agent where one instruction line would do
  • Never testing whether it changes the next run

Exercise 6 · Hand-in and toolkit

Pick the smallest building block that works

If you need…→ Use…
A rule that always applies to certain filesInstruction (narrow applyTo pattern; keep it short)
A workflow someone starts on demandPrompt file or skill entry point (slash command)
Deep know-how, question banks, templates or scriptsSkill (short SKILL.md; detail in reference files)
A multi-step job with tools, phases or hand-offsAgent (restrict its tools; hand off, don’t sprawl)
A rule that must hold whatever the model thinksControl: hook, permission, schema or CI check
Governed Azure DevOps/GitHub context or approved SharePoint/Teams evidenceApproved connector (MCP server); reuse an existing server before building one

Done when

Someone outside the team could install and run it from the specification alone, and a re-run of one RPI step shows the original correction is no longer needed.

Tips

  • Start with an observed correction, not a generic component idea. The proof is changed behaviour on the next run, not the size of the specification.
  • Least machinery: one well-reviewed skill beats ten private orchestrations.
  • Reuse the approved Azure DevOps MCP (opens in a new tab) or GitHub MCP server (opens in a new tab) for delivery context. Optional Work IQ (opens in a new tab) retrieves approved SharePoint/Teams evidence; it does not replace tracker-write approval.
  • Keep source access, allowed tools and failure behaviour in the component spec. Do not embed private Microsoft 365 excerpts or credentials in a reusable public skill.
  • APM lockfile governance is stable; its policy engine (apm-policy.yml) is an early preview, so pin the APM version.
  • Further reading: Agent Skills specification (opens in a new tab) and Model Context Protocol (opens in a new tab).
