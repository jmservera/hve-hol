Ejercicio 8 · Laboratorio abierto 4 · Tarea principal

Simulacro de revisión crítica entre equipos y recuperación

Tarea principalLaboratorio abierto 4

En esta páginaResumenCómo empezarEntrega y herramientasConsejos
Objetivo

Comprobar la solidez del proceso cuando se cuestiona, se interrumpe o es parcialmente incorrecto.

Material de partida
Los resultados de otro equipo
Uso recomendado
Tarea principal
Roles
Todo el equipo, emparejado con otro

Pasos

  1. Intercambiad artefactos, no explicaciones verbales.

  2. Cuestionad el contexto ausente, la seguridad, la capacidad de prueba, la preparación operativa y la trazabilidad.

  3. Introducid un fallo: ID de proyecto ausente, error de herramienta, experimento incompleto, contexto obsoleto o supuesto rechazado.

  4. El equipo original se recupera sin descartar en silencio la cadena de evidencias.

  5. Registrad qué fallos detectaron los controles, los agentes o las personas.

Entrega

Marca los elementos a medida que tu equipo los entregue.

Ejercicio 8 · Cómo empezar

Intercambiad artefactos y después provocad un fallo

Empieza aquí

  1. 1

    Emparejaos con el equipo que os indique quien facilita el taller; compartid un enlace a una rama o repositorio, no una demostración.

  2. 2

    Revisad sus artefactos durante 15 minutos desde las cinco perspectivas y anotad los hallazgos en la tabla.

  3. 3

    Entregadles una tarjeta de fallo; se recuperan mientras observáis, sin que les expliquéis el fallo.

  4. 4

    Intercambiad los papeles. Ambos equipos registran qué detectó cada fallo: un control, un agente o una persona.

Consejos prácticos

  • Agilizad con /rpi-review o el agente Code Review, en solo lectura sobre su rama; las personas deciden qué cuenta.
  • Seguid la cadena: evidencias, decisión, requisito, plan y resultado. ¿Dónde se rompe?
  • Derivad cada fallo a la primera fase responsable: investigación, planificación o implementación.

Errores que conviene evitar

  • Explicar en lugar de entregar artefactos
  • Borrar evidencias para que el relato quede limpio
  • Convertirlo en una revisión de estilo de código

Ejercicio 8 · Entrega y herramientas

Cuestionad con artefactos, recuperad con evidencias

Cinco perspectivas

  • Contexto

    ¿Qué falta, está obsoleto o carece de fuente?

  • Seguridad

    ¿Datos, secretos, permisos o contenido sensible?

  • Capacidad de prueba

    ¿Puede probarse cada criterio de aceptación?

  • Preparación operativa

    ¿Reversión, manual operativo, supervisión y traspaso?

  • Trazabilidad

    ¿Evidencias → decisión → requisito → plan → resultado?

Tarjetas de fallo (sacad una)

  • ID de proyecto ausente
  • Error de herramienta
  • Experimento incompleto
  • Contexto obsoleto
  • Supuesto rechazado

Las celdas de las plantillas son editables: escribe en ellas y usa Copiar como Markdown para pegar el resultado en tu repositorio o wiki. Lo que escribas permanece únicamente en este navegador; no se sube nada.

Registro de recuperación

FalloDetectado por (control · agente · persona)DecisiónDerivado a (investigación · planificación · implementación · nuevo elemento)Evidencias conservadas

Reglas de recuperación: registrar el fallo y la decisión · derivarlo a la primera fase responsable · nunca borrar evidencias para que el relato quede limpio

Ejecútalo con

  • HVE Core: el agente Code Review y /rpi-review comparan el trabajo con los requisitos y el plan, en solo lectura; /rpi-challenger pone a prueba los supuestos.
  • HVE-Squad: el estado del equipo y el registro de decisiones, que solo admite añadir entradas, se guardan en el repositorio; así el equipo puede retomar el trabajo tras una interrupción y mostrar quién decidió qué.

Enlaces

  • HVE Core · Flujo RPI (se abre en una pestaña nueva)
  • HVE Core · Planificación de seguridad (se abre en una pestaña nueva)
Terminado cuando

Cada equipo puede mostrar el fallo, quién o qué lo detectó y la cadena de evidencias aún intacta tras la recuperación.

Consejos

  • Emparejamiento: A con B, C con D; con cinco equipos, rotad (A revisa B, B revisa C … E revisa A).
  • Quienes facilitan el taller reparten las cinco tarjetas de fallo. El equipo revisor no puede explicar el fallo; el equipo original debe descubrirlo y gestionarlo.
  • Al final, contad los casos de «detectado por»: son una entrada valiosa para el ejercicio 10 y el canvas de adopción del ejercicio 9 (qué controles merece la pena automatizar).
