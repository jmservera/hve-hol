Ejercicio 7 · Laboratorio abierto 3 · Tarea principal · Empezad mientras se ejecuta el ejercicio 5

Puntos de aprobación humana y controles deterministas

Tarea principalLaboratorio abierto 3

En esta páginaResumenCómo empezarEntrega y herramientasConsejos
Objetivo

Separar las recomendaciones de los controles obligatorios y decidir dónde siguen respondiendo las personas.

Material de partida
Resultados del ejercicio 4 y del ejercicio 5 mientras se ejecuta
Uso recomendado
Tarea principal
Roles (sugeridos)
Responsable de calidad y gobierno y arquitecto

Pasos

  1. Enumerad todas las transiciones con consecuencias: aprobación de requisitos, elección de arquitectura, implementación, merge y publicación.

  2. Asignad un responsable y las evidencias necesarias para cada punto de aprobación.

  3. Clasificad cada regla: recomendación, aprobación humana o control determinista.

  4. Implementad o describid un control determinista: validación de esquema, comprobación de CI, límite de permisos o prueba.

  5. Simulad un punto de aprobación bloqueado y decidid qué evidencias hacen falta para continuar.

Entrega

Marca los elementos a medida que tu equipo los entregue.

Ejercicio 7 · Cómo empezar

Dibujad los puntos de aprobación y haced efectivo un control

Empieza aquí

  1. 1

    Empezad en cuanto se esté ejecutando el ejercicio 5; utilizad como entrada vuestros artefactos de los ejercicios 4 y 5.

  2. 2

    Dibujad el recorrido: aprobación de requisitos, plan, implementación, merge y publicación. Una fila del mapa de puntos de aprobación para cada uno.

  3. 3

    Clasificad cada regla: recomendación (por escrito), aprobación humana o control determinista.

  4. 4

    Haced efectivo un control, como la comprobación de merge, y mostrad cómo falla de forma intencionada.

Consejos prácticos

  • Para cada punto de aprobación, preguntad: ¿qué pasa hoy si alguien se lo salta? Si no pasa nada, es una recomendación.
  • Utilizad la CI que ya tenéis: Azure Pipelines o GitHub Actions.
  • Asignad una persona, no un rol, a cada punto de aprobación; indicad también quién puede autorizar una excepción y con qué evidencias.
  • Los agentes a veces se saltarán un paso: diseñad el control para ese caso.

Errores que conviene evitar

  • Responder a todos los riesgos con más instrucciones
  • Una comprobación que avisa, pero no bloquea
  • Un punto de aprobación sin responsable identificado

Terminado cuando

Un control bloquea algo de verdad, y el procedimiento de excepción identifica quién puede autorizarla y qué evidencias necesita.

Consejos

  • Preguntad: «¿Qué pasa hoy si alguien se salta este punto de aprobación?». Si la respuesta es «nada», la regla es una recomendación, diga lo que diga el documento de proceso.
  • Los agentes a veces se saltarán un paso; diseñad pensando en ello.
  • Una entrada de gitignore es una comodidad, no un control; el control es la comprobación obligatoria. Marcadla como obligatoria en las reglas de GitHub o las directivas de rama de Azure Repos.
  • Pedid a un administrador autorizado del repositorio/proyecto que configure las directivas obligatorias y gobierne los permisos para omitirlas. Un archivo YAML, una anotación de herramienta MCP o una instrucción por sí solos no hacen obligatorio el punto de aprobación.
  • El motor de directivas de APM está en una fase preliminar temprana.
  • Reutilizad el ciclo de operaciones de la actividad de espera B y el verificador de pasos de la actividad de espera C como entradas de vuestra matriz de controles.
