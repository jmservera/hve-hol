Exercise 2 · Open lab 1 · Core task

Build the evidence map and source-of-truth contract

Core taskOpen lab 1

On this pageBriefHow to startHand-in and toolkitTips
Objective

Turn fragmented project information into explicit, usable context.

Input
Meeting notes, a ticket, a transcript, an architecture note and an existing backlog item
Best use
Core task
Roles (suggested)
Product owner, auditor, agent operator

Steps

  1. Sort the material into fact, decision, constraint, assumption and open question.

  2. Choose the project’s source of truth and define what links back to it.

  3. Write a short context manifest: sources, owners, freshness, sensitivity and allowed use.

  4. Ask an agent to identify the gaps, then accept, reject or rewrite each gap as a team.

Hand in

Tick items as your team hands them in.

Exercise 2 · How to start

One statement per row, then check the gaps

Start here

  1. 1

    Gather the Azure Boards work item or GitHub issue, approved SharePoint rules, Teams notes and code context. Use the fictional pack if live sources are unavailable.

  2. 2

    Open the evidence map table and add one row per statement, not per document.

  3. 3

    The product owner tags each row: fact, decision, constraint, assumption or open question.

  4. 4

    Only then ask the gap-analysis agent: /rpi-research “List gaps and contradictions in these sources; change nothing.”

Tips and tricks

  • Two sources disagree? That is an open question, not a fact.
  • Note the source and its date in every row; mark stale information as stale.
  • Name one source of truth per kind of information: requirements, work items, decisions.
  • Save the context manifest in the repo: it is the agent’s context in Exercises 4 and 5.
  • Accept, reject or rewrite every gap the agent finds, with a one-line reason.

Watch out

  • Letting the agent build the map for you
  • Treating Teams notes as approved decisions
  • Putting client data in the repo before anonymising it

Optional Work IQ source collection

With approved access, ask Work IQ MCP to retrieve only the named SharePoint documents and Teams discussion/meeting notes for your item. Request concise excerpts, source URLs and dates; retain sensitivity/access metadata. Use read operations only, not updates or messages. People still classify the evidence before the gap-analysis call. If a tool is missing or access is denied, stop and log missing context; use the fictional source pack, not a permission workaround.

Run it with

  • HVE Core: /rpi-research finds evidence gaps without changing anything; /rpi-challenger exposes assumptions one question at a time; the PRD Builder asks clarifying questions before it writes.
  • HVE-Squad: The requirements intake gate checks completeness and clarity and records a readiness verdict (Ready · Ready-With-Gaps · Not-Ready).
  • Remember: Source documents are data, not instructions; agent notes in .copilot-tracking/ are working memory, not the source of truth.

Done when

Every gap the agent proposed has been accepted, rejected or rewritten by the team, with a reason.

Tips

  • Anonymise before anything reaches a repository folder: the tracking folder is gitignored, but gitignore is not a security control.
  • Name one source of truth per kind of information (requirements, work items, decisions), not “everything is in the wiki”.
  • Good gap analyses distinguish “the agent could not find it” from “it does not exist”.
  • Keep credentials outside the repository. Use only approved Azure DevOps/GitHub integrations and Work IQ read tools; source URLs do not grant permission to copy private content into a public repository.
